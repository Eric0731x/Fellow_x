## B. Ambiguous Requirements（歧义需求）

| # | 歧义点 | 问题 | 裁定（本 Spec 采用） |
|---|---|---|---|
| A1 | 等级命名不一致 | UI 规范用「铜/银/金/铂金/钻石」，原型数据用「萌新/同行者/实践家/布道者/核心」，阈值也不同 | 以**原型实现数据**为准：萌新0/同行者500/实践家1500/布道者4000/核心9000（BR-LV-01） |
| A2 | 取消已通过报名扣分数 | 文案出现「-5」与「-50」两处 | 以积分规则表 CANCEL_APPROVED = **-50 成长分**为准（BR-PT-04） |
| A3 | 「参与天数 / 连击」统计口径 | 何为「有效参与」、连击如何中断 | 定义：完成可计积分行为计入参与天数；自然日无活跃则连击归零（待产品二次确认） |
| A4 | 活动 summary vs description | UI 字段名混用 | 统一为 summary（列表）+ content（详情富文本）（schema §4） |
| A5 | 谁能让活动「开放报名/开始/结束」 | 发起人 or 系统自动 | 二者皆可且幂等：发起人手动 + 到点自动（BR-AC-09） |
| A6 | 福利「8 折特权」是否本期生效 | 等级特权写了折扣但无结算规则 | 本期默认关闭，规则与开关预留（BR-RW-06） |
| A7 | Admin 是否能创建/代管活动 | 未明确 | 否，保持发起人负责制（PERMISSION 脚注 3/4） |
| A8 | 报名是否需要审批 | 详情页「立即报名」易被理解为即时通过 | 报名即 PENDING，需发起人审批（BR-RG-04） |
| A9 | 兑换积分能否为负 / 成长分扣到负 | 未定义下限 | 均不可为负，扣减越界拒绝（BR-PT-08） |

## C. Potential Risks（潜在风险）

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | **超卖/超额**：高并发报名审批与兑换若用「先查后写」会竞态 | 高 | 乐观锁条件更新 + 唯一约束（BR-RG-02/RW-02） |
| R2 | **积分账不平**：余额冗余与流水不一致 | 高 | 单事务三写 + balance_after 快照对账（BR-PT-07/10） |
| R3 | **发分重复**：活动结束/手动+自动双触发导致重复发分 | 高 | 以 activity_id 幂等去重（BR-AC-06） |
| R4 | **权限绕过**：前端守卫被当唯一防线 | 高 | 后端每写接口独立校验权限+所有权（PERMISSION §4 红线） |
| R5 | **状态机漏判**：非法转换未拦截造成脏状态 | 中 | 集中状态机服务 + 409 拒绝 + 单测覆盖全转换 |
| R6 | **时区错乱**：活动时间/截止跨时区 | 中 | UTC 存储、ISO 8601 传输、前端本地化 |
| R7 | **不降级与晋级竞态**：阈值调整与积分变更并发 | 中 | 等级只随积分增量上升，配置变更不触发重算（BR-LV-03） |
| R8 | **大富文本/XSS**：content 用 v-html 渲染 | 中 | 服务端富文本白名单清洗 + 前端净化 |
| R9 | **上传滥用**：超大/恶意文件 | 中 | 大小/类型/魔数校验，独立对象存储 + 限频 |
| R10 | **通知风暴**：批量取消/发分群发通知 | 低 | 异步队列 + 去重（BR-NT-02） |
| R11 | **AI Agent 误解枚举**：中文状态名 vs 英文枚举混用 | 中 | 全链路统一英文枚举（schema §13），中文仅展示层 |

## D. Suggested Improvements（改进建议）

1. **统一术语表**：将等级、状态、积分类型固化为单一英文枚举来源（已在 schema §13），所有文档/代码引用之，杜绝 A1/A11。
2. **以事件驱动重写状态机**（已做 STATE_MACHINE.md），让 Agent 能直接据此生成 service + guard + 测试。
3. **抽象统一组件契约**：StatusBadge / ConfirmDialog / RejectDialog / EmptyState / Skeleton 等先于业务页交付（已列入 PAGE_STRUCTURE §4、Phase 0）。
4. **把"可配置 vs 固定"显式化**（已做 BUSINESS_RULES §9），指导哪些进后台、哪些写代码。
5. **补齐非功能需求**：性能（列表分页/索引）、安全（鉴权/清洗/限频）、可观测（审计/日志/埋点）、幂等（发分/生命周期）——已分散落入各 Spec 与横切关注点。
6. **为每条业务规则编号**（已做 BR-xx-nn），便于在测试与 PR 中追溯。
7. **明确 MVP 边界**：实物履约、福利折扣、批量审批等标记为扩展项，避免首版范围蔓延。

## 结论
原 PRD 在**产品叙事、角色、旅程、状态语义、异常意识**上已相当完整，是优秀的产品文档；但作为**驱动 AI Agent 开发的工程契约**，缺少数据/API/权限/状态机的机器可执行精度，并存在若干术语歧义与并发一致性盲区。本 Spec 体系（DATABASE_SCHEMA / PERMISSION_MATRIX / API_SPEC / PAGE_STRUCTURE / STATE_MACHINE / BUSINESS_RULES / TASK_BREAKDOWN）已逐项补齐，详见 READINESS.md 的开发准备度评估。
